1. Project Overview
System Purpose
EduTrack
 is a web-based Student Enrollment & Records System for a college. It lets the registrar manage subjects and schedules, students enroll in and drop subjects online, faculty encode grades, and finance staff record payments — all behind role-based logins. Because the system stores personal data, academic records, and payment information, security is a primary design concern rather than an afterthought.
Target Users
Admin / 
Registrar:
 
manages users, subjects, schedules, and oversees enrollment and records.
Faculty: 
views class lists and encodes or edits grades for assigned subjects.
Students: 
enroll in or drop subjects, view their own schedule, grades, and balance.
Cashier / Finance: 
records payments and generates assessment and collection reports.
IT Administrator: 
configures system and security settings and reviews audit logs.
Key Features
Role-based login with JWT authentication and optional MFA (TOTP).
Online enrollment: add and drop subjects with real-time slot checking.
Grade encoding and editing by faculty, with change history.
Student record and profile management (registrar).
Subject, section, and schedule management.
Payment recording and assessment view (finance).
Reports and exports (enrollment, grades, collections) to PDF / Excel / CSV.
Audit logging of logins and critical actions.
Password policies, account lockout, and rate limiting.
In-Scope
Enrollment, records, grades, scheduling, and payment recording.
Authentication, roles, and permission management.
Reporting, analytics, and data export.
Security and compliance features (audit logs, password policies, MFA).
Out-of-Scope
Learning-management features (course content, quizzes, submissions).
Native mobile applications.
Online payment gateway / card processing (payments are recorded, not charged).
Government reporting integrations (e.g., CHED) unless custom-built.

3. Functional Requirements
The system shall allow students to enroll in and drop subjects, validating available slots and prerequisites.
The system shall allow the registrar to create, edit, and archive subjects, sections, and schedules.
The 
system shall
 allow faculty to encode and edit grades only for subjects assigned to them.
The system shall store and manage student profiles, including contact details and academic records.
The system shall allow finance staff to record payments and generate assessment and collection reports.
The system 
shall
 provide role-based access control, restricting features and data by user role.
The system shall authenticate users via JWT and support multi-factor authentication for staff accounts.
The system shall log all authentication attempts and critical actions (grade edits, enrollment changes) with user, timestamp, and IP.
The system shall allow authorized users to export enrollment, grade, and payment data to PDF, Excel, and CSV.
The system shall enforce password policies and lock an account after five consecutive failed logins.
The system shall allow the IT administrator to configure system settings (terms, MFA policy, lockout thresholds).
The system shall display clear validation messages for all invalid user input.
4. Non-Functional Requirements
Security
The system shall require JWT authentication for all protected resources.
The system shall enforce strong passwords (min 8 chars, mixed case, digit, special character) and store them only as salted hashes.
The system shall support MFA (TOTP) for all staff accounts.
The system 
shall
 use HTTPS/TLS for all communication.
The system shall lock accounts for at least 15 minutes after 5 failed login attempts.
The system shall restrict data access based on role and resource ownership.
Performance
The system shall respond to user actions within 2 seconds for 95% of requests under normal load.
The system shall support at least 50 concurrent users without performance degradation.
The system shall complete exports of up to 10,000 records within 30 seconds.
Usability
The system 
shall
 provide a responsive interface for 
desktop
, 
tablet
, and 
mobile
.
The system shall let a student complete enrollment in no more than 5 steps.
The system 
shall
 provide meaningful error messages for all input errors.
Reliability
The system 
shall
 be available 99.5% of the time, excluding scheduled maintenance.
The system shall back up critical data at least once every 24 hours.
The system shall recover from restarts without data loss and handle network errors gracefully.
5. System Architecture
Explanation
Users interact with a React single-page frontend, which 
calls
 the ASP.NET Core 8 Web API over HTTPS.
The API handles business logic, authentication, and authorization, and reads/writes SQL Server through Entity Framework Core.
An external email/SMS service delivers one-time passwords and alerts.
Security is enforced at the API layer: JWT validation, role and ownership checks, rate limiting, and MFA.
All requests cross a single trust boundary at the API — the frontend never talks to the database directly.

9. Security Documentation
Authentication
JWT bearer authentication; a signed token is issued on successful login and sent in the Authorization header.
MFA via TOTP for staff; tokens expire and can be refreshed; accounts lock after repeated failures.
Authorization (Roles & Permissions)
Role-based access control enforced at the API with [
Authorize(
Roles=...)] and custom policies.
Resource-ownership checks ensure users access only their own records (no IDOR).
Input Validation
Server-side validation via data annotations (required fields, length, numeric ranges, email format), mirrored by client-side checks.
Data Protection (Hashing / Encryption)
Passwords stored as salted PBKDF2 hashes (never plaintext).
HTTPS/TLS in transit; secrets (JWT key, connection string) kept out of source control.
Preventing SQLi / XSS / CSRF
SQL Injection: 
all data access goes through EF Core parameterized queries; no string-concatenated SQL.
XSS: 
output is encoded by default; rich text sanitized before render.
CSRF: 
anti-forgery tokens required and validated on all state-changing requests.
Additional Measures
Rate limiting on auth endpoints, audit logging of critical actions, a strict CORS allow-list, and HTTPS-only deployment.

13. Maintenance & Future Work
Known Limitations
Permissions are role-level only; no per-record delegation yet.
Reports offer limited filtering and no interactive charts.
No automated security scanning runs in 
the build
 pipeline.
Backups are scheduled but not yet tested with a full restore drill.
Planned Improvements
Single Sign-On (OAuth/OpenID Connect) so the school can use existing accounts.
Add automated SAST/dependency scanning (e.g., in CI) to catch new vulnerabilities early.
Finer-grained, attribute-based access control for special cases.
Performance: query optimization and caching of read-heavy pages (schedules, dashboards).
Accessibility and responsive-design pass (WCAG) for all core screens.
Security dashboard summarizing audit logs, failed logins, and lockouts.
